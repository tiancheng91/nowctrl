# P0 validation — 2026-10-20 (Asia/Shanghai)

Status: **P0 not accepted**. Host builds and emulator evidence below do not
certify real-board radio, phone connectivity, or AP/ESP-NOW coexistence.

## Reproduction baseline

- Host: macOS Apple Silicon (`aarch64-apple-darwin`).
- Rust/Cargo: 1.99.1; target `riscv32imc-unknown-none-elf`.
- esp-rs revision: `c21d5741a8fdecb9e01b196e55b7c7859360bf1b`, matching the official
  `examples/esp-now/embassy_esp_now_duplex` source inspected in the local checkout.
- Locked packages include esp-hal 1.2.0, esp-radio 1.0.0-beta.2, esp-rtos 0.4.0,
  esp-bootloader-esp-idf 0.6.0, embassy-executor 0.10.0 and embassy-time 0.5.1.
- Image generator: espflash 4.4.0 (`cargo install espflash --version 4.4.0 --locked`).
- Emulator: ESP-EMU 0.49.0, installed at `$HOME/.local/bin/esp-emu` on this host.
  The wrapper uses PATH or `ESP_EMU_BIN`, not that host-specific path.
- Image assumption: ESP32-C3, 4MB flash, espflash default bootloader/partition table.
  No physical board flash size or LED profile has been confirmed.

## Implementation and checks

The original task spawning used the older Embassy API. It now unwraps task
creation before passing the token to `Spawner::spawn`, matching the pinned
upstream example. All direct esp-hal repository dependencies share an explicit
revision. The generated Cargo.lock is included in the delivery; nothing has been
committed or pushed.

Startup logs identify role, RF channel 6 and station MAC. A separate Embassy task
logs one-second ticks. The main task yields for three seconds before synchronous
radio initialization; both emulator and physical firmware use this same path.
TX logs carry a wrapping local sequence counter; the existing discovery payloads
are unchanged. The counter is diagnostic only, not a protocol request ID.

See [scripts and usage](../../sim/esp-emu/README.md). Build logs retain actual
commands/results; emulator logs retain UART output and errors.

## Physical validation procedure (P0.3, pending)

1. Identify each board's manufacturer/profile, flash size, BOOT GPIO and strap
   behavior, LED type/pin/polarity, serial port and download procedure. Do not
   drive an assumed LED pin. No actuator should be connected.
2. Build both roles with the pinned tools. Flash the matching role ELF using
   `espflash flash --chip esp32c3 --port <verified-port> --monitor <role-elf>`.
   Record board profile, role, build revision, MAC and startup log for each board.
3. At RF channel 6, capture each board receiving the opposite role's broadcast.
   Current firmware has **no unicast exchange**; add a discovery-only unicast
   experiment before claiming the bidirectional-unicast gate. Record sender MAC,
   receive payload and monotonic sequence once that probe exists.
4. Power-cycle each board independently and together; verify discovery resumes.
   Capture failures as well as successful recovery.
5. In a separate P0 probe on the same locked driver, implement protected temporary
   SoftAP plus minimal HTTP. Verify phone association, DHCP and HTTP, then repeat
   radio exchange while HTTP is active. Record AP channel and radio errors.
6. If coexistence fails, implement an explicit exclusive setup mode, disable
   control there and test transitions/recovery. A planned fallback is not a pass.

No ESP32-C3 serial device was identified during this run. Two-board exchange,
phone HTTP, AP coexistence, physical GPIO and current consumption remain
**not tested**. P1+ remains out of this iteration.

## Emulator observations and blocker

Reproduction (requires the pinned tools on PATH, or their `*_BIN` overrides):

```sh
python3 sim/esp-emu/p0.py build controller
python3 sim/esp-emu/p0.py build node
python3 sim/esp-emu/p0.py run controller --seconds 20
python3 sim/esp-emu/p0.py run node --seconds 20
```

Both `run` commands intentionally return **1** on this baseline: the emulator
itself exits 0 at its timeout, but the wrapper finds no consecutive timer ticks.
An emulator timeout exit is not firmware success.

| Capability | Controller | Node |
| --- | --- | --- |
| ROM + ESP-IDF bootloader reads merged image | Observed | Observed |
| Rust application startup marker | Observed | Observed |
| HAL initialization and MAC read | Observed | Observed |
| RTOS start returns | Not observed within 20 wall-clock seconds | Not observed within 20 wall-clock seconds |
| Three consecutive Embassy ticks | FAIL / blocked | FAIL / blocked |
| GPIO / physical LED | Not tested; board profile unknown | Not tested; board profile unknown |
| ESP-NOW initialization / TX / RX | Not reached | Not reached |
| Multi-instance ESP-NOW delivery | Not tested | Not tested |
| Firmware SoftAP / HTTP / coexistence | Not implemented in this iteration; not tested | Not applicable |

The default emulator console initially showed only bootloader output. A separate
[USB console probe](logs/controller-usb-console-probe.log) exposed application
logs. esp-println's auto transport observes the USB SOF flag, whereas the
emulator's auto console does not necessarily select the same stream. The launcher
therefore explicitly selects `--console usb-jtag`; firmware transport and
production architecture are unchanged.

Final normal-boot evidence: [Controller UART/USB output](logs/controller-emulator.log),
[Node UART/USB output](logs/node-emulator.log),
[Controller failed smoke check](logs/controller-smoke.log), and
[Node failed smoke check](logs/node-smoke.log). The earlier
[Node default-console log](logs/node-initial-emulator.log) is retained as well.

Both final logs end after the same stages (role differs):

```text
NOWCTRL BOOT role=controller rf_channel=6
NOWCTRL HAL ready
NOWCTRL MAC MacAddress([36, 10, 196, 0, 0, 1])
NOWCTRL RTOS starting
```

The MAC shown is emulated; both instances share that default identity and this
is not evidence of unique real-device MACs. No `NOWCTRL RTOS ready`, tick,
`NOWCTRL RADIO initializing`, TX or RX was observed. Thus the current blocker is
**at RTOS startup, before radio initialization**, not an established ESP-NOW
unsupported conclusion.

A separate bounded GDB probe interrupted the Controller while waiting and saved
[registers](logs/controller-debug-probe.log) plus a local ELF
[symbol lookup](logs/controller-debug-symbol.log). The sampled PC maps into
`SoftwareInterrupt<0>::raise`. This is a diagnostic lead for the emulator's
software-interrupt/scheduler interaction, not proof of the root cause. No driver
patch, scheduler substitution or emulator-only firmware bypass was introduced.
The next investigation should compare interrupt delivery against this pinned
esp-rtos implementation; physical tests may proceed independently.
